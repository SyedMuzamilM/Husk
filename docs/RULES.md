# Cleanup rule acceptance

Rules identify exact tool-owned paths; they cannot execute commands. A path name such as cache, build, or dist does not prove disposability.

A rule submission must record supported app/tool versions, primary-source path evidence, data contents, owner bundle ID when known, loss/rebuild consequences, current-use checks, and fixtures. Credentials, browser profiles, mail/messages, cloud data, installed tools, whole model stores, virtual disks, shared group containers, and unverified project outputs are excluded from bulk cleanup.

Safe means documented regeneration of the exact data class, not "probably junk". Offline downloads, histories, virtual environments, local dependency edits, and diagnostics require Review/Caution or an inspection-only rule. Default selection must never include Review/Caution. Running known owners must block removal; unknown owner status is a limitation to disclose.

All measurements must include hidden/package contents, avoid symlinks/cloud hydration and volume crossing, and report errors/truncation. Allocated-byte estimates cannot promise reclaimed space. Target sets and plans must deduplicate exact/nested paths. Exclusions apply again at mutation time.

Required tests include name collisions, protected parent/child, symlink ancestor/leaf/swap, changed identity, excluded child beneath selected parent, partial sizing, duplicate targets, cancellation, and mixed Trash outcomes. Project cleanup needs Git-tracked-content and nested-repository protection plus manifest/activity evidence before enabling deletion. Current project discovery remains inspection-only.
